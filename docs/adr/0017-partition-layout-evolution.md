# 分割表的演進規則：M6 不改，nvs／phy／factory 永遠不動，新分割區只從 storage 切

M6 要把學到的線色與物體範本存起來（「設定好拔掉電腦、R4 單獨運作」，SPEC §1），之後 M7–M9 還有更多模型與學習資料。分割表從 M0 起沒變過：

| 名稱 | 位置 | 大小 |
|---|---|---|
| `nvs` | 0x9000 | 24K |
| `phy_init` | 0xF000 | 4K |
| `factory` | 0x10000 | 4M |
| `storage` | 0x410000 | 0xBF0000（到 16 MB 結尾，保留給模型） |

決定：

1. **M6 不改分割表**。學到的線色與物體放進現有 NVS 的同一個 store blob（v3，最大 2,993 B，`mxcam_store.h`）：24 KB 的 NVS 寫新 blob 時新舊並存也只要約 6 KB，SAVE 仍是一次原子寫入，FACTORY_RESET 照樣清掉。v3 讀得了 v1、v2（舊韌體存的顏色、名字、設定燒新韌體後都還在）。
2. **`nvs`、`phy_init`、`factory` 的位置與大小永遠不動**。之後需要的新分割區一律從 `storage`（0x410000 起）切。
3. **預定版面**（真的需要時才改，例如 ADR-0019 說的「第三個 NN 模型放不下 factory」）：`mxdata`（NVS，256K，固定放在 0x410000、`storage` 的最前面）→ esp-dl 指定名稱的模型分割區（`pedestrian_det`、`hand_det`、`hand_gesture_cls`、`human_face_feat` 等，大小到時實測）→ 剩下的仍叫 `storage`。`mxdata` 放最前面，之後模型分割區變大變小都不會移動它。
4. **只燒 app、分割表還是舊的**（例如 M5 網頁燒錄預設只寫 bootloader／分割表／app、或使用者自己 `idf.py app-flash`）：韌體開機時找不到需要的分割區，就把相關功能從 GET_INFO 拿掉、其他功能照常（和模型載入失敗相同的處理，ADR-0011、ADR-0019），不可以當機或卡住開機。
5. **修正 M5 計畫（ADR-0014 草稿）「之後若改分割表就要強制完整清除」的條件**：M5 網頁燒錄預設保留 0x9000 的 NVS；只要 `nvs` 不動，改分割表（從 `storage` 切新分割區）並不會讓學到的資料失效，所以**只有 `nvs`／`phy_init`／`factory` 移動時才需要強制完整清除**——而第 2 點規定它們不動。

## Considered Options

- **M6 就切好模型分割區**：模型大小要到 M7／M8 實測才知道，現在切等於之後再改一次；M6 需要的空間 24K NVS 就夠。
- **把 `nvs` 加大或搬家**（例如 64K 放到別處）：M5 網頁燒錄保留的是 0x9000 那一段，NVS 一搬，燒新韌體後就讀不到舊的學習資料；加大也會推動後面的 `phy_init`／`factory`。
- **學到的物體只放 RAM**：斷電就不見，與「拔掉電腦單獨使用」衝突（ADR-0018）。

## Consequences

- store blob 的大小上限現在約 3 KB（`MXST_BLOB_MAX` 2,993）；內部 RAM 多約 1.5 KB（`mxs_data_t` 1,784 → 2,900 B，main 與存檔工作各一份；load／save 改成共用一個 blob 緩衝區）。
- 之後更大的學習資料（M9 人臉特徵、自學習分類）不該再塞進這個 blob，而是放到第 3 點的 `mxdata`；名字表 32 筆到時也一起加大（SPEC §10）。
- 第一次真的改分割表時，要同時實作第 4 點的「找不到分割區」處理並在實機上只燒 app 驗證。
