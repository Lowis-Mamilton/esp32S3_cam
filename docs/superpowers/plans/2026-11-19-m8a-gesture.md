**目標：** MXCam 能辨識 9 種固定手勢（功能 8）：韌體偵測手＋分類手勢，TFT 畫框與手勢名稱，USB 推送結果，參數與手勢名字可存檔；MXCam Studio（真板子與展示模式）能選手勢功能、看結果、調參數、幫手勢取名。

**架構：** 新元件 `mxcam_gesture`（照 `mxcam_face` 的做法：C 介面包 C++）包裝 Espressif `hand_detect`（找手）＋`hand_gesture_recognition` 的 `HandGestureCls`（每隻手裁切後分類），純 C 的後處理 `mxcam_gesture_post.c` 可在電腦上測。兩個模型放 app 的 flash rodata、開機時在 ADR-0011 的「malloc 導到 PSRAM」時段內載入；處理流程（core 1）在功能 8 時每張畫面同步辨識。參數走 ADR-0016 的 `GET_FUNC_CONFIG`／`SET_FUNC_CONFIG`（Gesture config v1），存進 store blob v2。

**技術：** ESP-IDF v5.5.6、esp-dl 3.3.15（已鎖定）、`espressif/hand_detect` 0.2.1、`espressif/hand_gesture_recognition` 0.2.1、純 C99 host test、React/TS（Vitest）。

**規格：** `docs/SPEC.md` §3（擴充功能表：8 手勢辨識，NN 功能 ≥ 3 fps）、§6.1；`docs/research/vision-functions.md` §1、§4.1、§5；`docs/protocol.md` §4、§7、§9；ADR-0010、0011、0016。

## 設計決定（執行時寫進 SPEC／protocol.md／ADR；理由附在後面）

1. **模型與版本（2026-11-19 查 ESP Component Registry 與元件原始碼確認）**：`espressif/hand_detect` `~0.2.1`（依賴 esp-dl `~3.3.14`）與 `espressif/hand_gesture_recognition` `~0.2.1`（依賴 hand_detect `~0.2.0`），兩者 MIT、2026-10-22 發佈，與已鎖定的 esp-dl 3.3.15、`human_face_detect` 0.5.2、IDF v5.5.6 相容。模型：`espdet_pico_224_224_hand.espdl`（S3 版 497,184 B；輸入 224×224，letterbox；README 延遲 7.6＋120.1＋0.9 ms）、`mobilenetv2_0_5_128_128_gesture.espdl`（787,296 B；每隻手裁切成 128×128；4.2＋69.2＋0.5 ms／手）。**README 的延遲是在 64 KB 資料快取、64 B 快取線下量的，我們是 32 KB／32 B，預期更慢**（Task 1 實測）。類別（esp-dl `vision/classification/hand_gesture_category_name.hpp`，順序即模型輸出）：`one, two, three, four, five, like, ok, no_gesture, call, dislike, no_hand`。API：`HandDetect(model_type, lazy_load)` 的 `run(img)` 回 `std::list<dl::detect::result_t>`（`box = {x0, y0, x1, y1}`、`score`，框已換回原圖座標）、`set_score_thr(thr, 0)`；`HandGestureCls(model_type, lazy_load)` 的 `run_crop(img, {x0, y0, x1, y1})` 回 `std::vector<dl::cls::result_t>`（`cat_name`、softmax 後的 `score`，top-1）。Kconfig：`CONFIG_FLASH_ESPDET_PICO_224_224_HAND`、`CONFIG_ESPDET_PICO_224_224_HAND`、`CONFIG_HAND_DETECT_MODEL_IN_FLASH_RODATA`、`CONFIG_FLASH_HAND_GESTURE_CLS_MOBILENETV2_0_5_S8_V1`、`CONFIG_HAND_GESTURE_CLS_MOBILENETV2_0_5_S8_V1`、`CONFIG_HAND_GESTURE_CLS_MODEL_IN_FLASH_RODATA`（皆為預設值，照人臉的做法寫進 `sdkconfig.defaults`）。**不用 `HandGestureRecognizer`**：它內部的分類器是 lazy load（第一張畫面才載入，在 malloc 導向時段之外，會吃內部 RAM）、會對最多 10 個偵測框全部分類（時間無上限）、沒有手時每張畫面印一次 warning。
2. **模型位置：app 的 flash rodata，不改分割表（Task 1，ADR-0019）**：目前映像 2,233,072 B（`firmware/build/mxcam.bin`）＋兩個模型 1,284,480 B＋程式約 20–60 KB ≈ 3.54–3.58 MB，factory 4 MB（4,194,304 B）剩約 0.6 MiB（約 15%）。規則：Task 1 量到的映像 **≤ 3,774,873 B（4 MiB 的 90%）** 就用 rodata；超過就停下來回報主對話（改走模型分割區，另開計畫）。理由：不動分割表＝M5 網頁燒錄（bootloader／分割表／app 三個映像、保留 NVS）完全不受影響，M5 計畫的 precache 上限 8 MiB 也放得下約 3.5 MB 的 app；不用改 ADR-0017（M6 Task 4 預定）的分割表規則；最快把手勢做出來。後果：**第三個 NN 模型（功能 7 人體 435 KB、功能 9 人臉特徵 1.3 MB）一定放不下**，屆時照研究 §5.1 把手勢模型連同新模型一起搬到 `hand_det`／`hand_gesture_cls` 分割區（只是改 Kconfig 的位置選項＋分割表，元件程式不用改），記到 SPEC §10。
3. **載入：開機時載入，延伸 ADR-0011 的 malloc 導向時段（Task 1，ADR-0019）**：`mxh_init` 在 `app_main` 裡緊接在 `mxf_init` 之後、建立任何應用程式 task 之前呼叫，自己也用 `heap_caps_malloc_extmem_enable(0)` 包住建構（兩個 C++ 物件都用 `lazy_load = false` 立刻載入）。PSRAM 估計 1.8–2.6 MB（以人臉 191 KB 模型佔約 425 KB 的比例推估），開機後 PSRAM 約 5.9 MB 可用，夠；開機時間估計多 0.2–0.5 s。初始門檻 `MXH_MIN_PSRAM_FREE` = 3 MiB、`MXH_MIN_INTERNAL_FREE` = 64 KB（同人臉）；Task 1 實測後把 PSRAM 門檻改成「實測用量＋1 MiB」。規則：開機完成時 PSRAM 剩餘 **≥ 2 MiB**（AprilTag 執行時會配置 PSRAM、heap guard 要 256 KB 區塊）、內部 RAM 最低 **≥ 60 KB**、開機載入 **≤ 1 s**；任一條不成立就停下來回報主對話（改成切換功能時才載入，另開 ADR）。失敗時功能 8 不列在 GET_INFO，其他功能照常（同 ADR-0011）。理由：切換時才載入需要「SET_FUNCTION 延後回應」、不能用全域 malloc 導向（研究 §5.2 的 B／C 做法，B 會多吃約 15 KB×2 內部 RAM、C 要先驗證 `operator new` 導向），範圍大很多；PSRAM 目前用不完。後果：人體、人臉辨識加入時 PSRAM 會不夠（估計合計 > 5.9 MB），屆時再做按需載入，記到 SPEC §10。
4. **每張畫面同步辨識，TFT 跟著辨識速度更新（Task 4，ADR-0019）**：功能 8 在 core 1 的處理流程裡每張畫面都跑 `mxh_detect`（照人臉的做法，不另開 NN task、不降頻）。預期一隻手約 4–5 fps、沒有手約 6–7 fps、兩隻手約 3–3.5 fps（TFT 與網頁預覽都是這個速度）。理由：協定的 RESULTS 和 FRAME 用同一個 `frame_id` 對應，非同步辨識會讓框對到比結果新的畫面（手在動時框落後約 200 ms），還要多一份 150 KB 畫面複製與同步；core 0 在串流時忙 JPEG，沒有空閒核心可用。速度不夠時的退路（依序，Task 1 量測決定）：一隻手平均 > 300 ms 時先試 `CONFIG_ESP32S3_DATA_CACHE_LINE_64B=y`（不花內部 RAM，但影響全部功能，要重量顏色／AprilTag／人臉）；**不改 64 KB 資料快取**（要多 32 KB 內部 RAM，會讓最低剩餘逼近 60 KB 底線）。用到退路就寫進 ADR-0019 與 m8a.md。
5. **辨識結果（Task 2，protocol.md 新 §10）**：每隻偵測到的手一筆，最多 `max_hands` 筆（1–2）。
   - **手勢 ID 表**（照模型輸出順序，跳過 `no_gesture`；1–5 剛好是「比幾根手指」，學生好記）：

     | id | 模型類別 | TFT（ASCII） | 中文 | English |
     |---|---|---|---|---|
     | 0 | `no_gesture`、`no_hand`、或分數低於門檻 | `HAND` | 手（認不出手勢） | Hand (unknown) |
     | 1 | `one` | `ONE` | 一 | One |
     | 2 | `two` | `TWO` | 二（YA） | Two |
     | 3 | `three` | `THREE` | 三 | Three |
     | 4 | `four` | `FOUR` | 四 | Four |
     | 5 | `five` | `FIVE` | 五（張開手掌） | Five |
     | 6 | `like` | `LIKE` | 讚 | Like |
     | 7 | `ok` | `OK` | OK | OK |
     | 8 | `call` | `CALL` | 打電話 | Call |
     | 9 | `dislike` | `DISLIKE` | 倒讚 | Dislike |

     對應用 `cat_name` 字串比對（大小寫完全相同），不用索引，上游改順序也不會錯；不認得的名稱 → 0。
   - `id` = 手勢 ID；手勢分數 ×100 低於 `gesture_threshold`、或類別是 `no_gesture`／`no_hand` → `id = 0`（**仍然回報這隻手**，跟 HUSKYLENS「ID 0 = 沒學過」一樣；R4 只看特定 ID 就自然略過）。
   - `x, y, width, height` = 手的框（中心＋寬高），320×240 真實影像座標（ADR-0010），已裁到畫面內。
   - `confidence` = 這筆紀錄「宣稱的東西」的分數：`id ≥ 1` 時 = round(手勢分數 ×100)；`id = 0` 時 = round(手的偵測分數 ×100)。
   - `extra_len = 0`（R4 端最簡單；手的偵測分數只用在篩選與排序）。
   - 篩選與排序：偵測分數 ×100（四捨五入）< `hand_threshold` 的手丟掉；裁切後寬或高 < 16 px 的手丟掉（太小分類不可靠，也避免 esp-dl 裁切 0 大小的區域）；其餘依偵測分數由高到低（同分時框大的在前、再依偵測器順序），**只取前 `max_hands` 隻去分類**（時間上限 = 1 次偵測＋`max_hands` 次分類）。
6. **名字（Task 3）**：手勢 ID 是固定類別，和 AprilTag 一樣**可以取名、不需要學習**：SET_NAME 8 接受 `id` 1–9（0 與其他 → `BAD_PARAM`）；GET_LEARNED 8 回有名字的手勢（依 ID 排序，`r, g, b` 填 0）；FORGET 8 刪名字（`0xFFFF` 刪全部手勢名字），不存在也回成功；LEARN 8 → `BAD_PARAM`。名字表仍是全部功能合計 32 筆。TFT 只顯示 ASCII 名稱（名字是 UTF-8），Studio 有名字時顯示名字。理由：學生想讓「讚」叫「前進」；照 AprilTag 的規則，主機程式與 Studio 都有現成的流程。
7. **參數：Gesture config v1（function_id 8，layout_version 1，body 8 bytes，整包 10 bytes；Task 2，ADR-0016 的做法）**：

   | 欄位 | 型別 | 預設 | 範圍／夾限 | 說明 |
   |---|---|---|---|---|
   | hand_threshold | u8 | 40 | 10–95（夾到邊界） | 手的偵測分數門檻（×100）；低於它的手不回報 |
   | gesture_threshold | u8 | 60 | 0–100（> 100 → 100） | 手勢分數門檻；低於它的手回報成 `id 0` |
   | max_hands | u8 | 1 | 1–2；0 → 1、> 2 → 2 | 最多回報幾隻手（每多一隻約多 75 ms） |
   | reserved | u8 ×5 | 0 | | |

   `max_hands` 預設 1：兩隻手約 3–3.5 fps，剛好在 NN 目標 3 fps 邊緣；R4 互動通常一隻手。`hand_threshold` 預設 40 是暫定值：上游預設 0.25；**Task 1 實測真手的偵測分數中位數 < 0.55 時改成 30**，Task 2 以 Task 1 寫在 `docs/measurements/m8a.md` 的值為準（測試資料只能新增不能改，所以要在 Task 2 之前定）。不做「最小手大小」參數（固定 16 px）、不做「回報 id 0 與否」的開關（YAGNI）。
8. **store blob v2：通用的 func config 紀錄清單（Task 3）**：v2 = v1 的全部內容（`version = 2`）＋ `n_fcfg u8` ＋ `n_fcfg ×` 10 bytes（就是 SET_FUNC_CONFIG 的整包：`function_id, layout_version, body 8`）＋ CRC16。讀取時：v1 → 手勢參數用預設；v2 的紀錄中 `function_id 8` 且 `mxp_unpack_gesture_config` 成功 → 套用；**不認得的功能或版本 → 略過**（不判整包壞掉）；同一個已知功能出現兩次 → 整包拒絕（資料損毀）；`n_fcfg` > 16 → 拒絕。`MXST_MAX_FCFG 16`，`MXST_BLOB_MAX` 從 1719 變 1880。理由：M6 的線條／物體參數之後只要加進同一份清單、不用再升版本；略過不認得的紀錄讓之後的參數版面升級不會清掉使用者的其他資料。
9. **service（Task 3）**：新增 `GET_FUNC_CONFIG`／`SET_FUNC_CONFIG` 的處理，結構是「依 `function_id` 的 switch」，本計畫只有 `case MXP_FUNC_GESTURE`，M6 Task 4 再加 4／5。錯誤順序照 protocol.md §9：GET 長度不是 1／SET 是空的 → `BAD_LENGTH`；功能沒有 func config **或 GET_INFO 沒列出** → `BAD_PARAM`；SET 長度不是 10 → `BAD_LENGTH`；`layout_version` 不符 → `BAD_PARAM`。值真的改變才 `mark_dirty`；FACTORY_RESET 經由 `mxst_defaults` 回預設；SAVE 的快照自然包含。**注意：M6 計畫 Task 4 寫「只接受 4、5（不看能力清單）」，與 protocol.md §9「GET_INFO 沒列出的功能 → BAD_PARAM」矛盾；以 protocol.md 為準**，本計畫照它實作，並記到 SPEC §10 給 M6 Task 4。順便修正延續下來的問題：GET_INFO 的暫存 `buf[23 + 8]` 改成 `23 + MXP_INFO_MAX_FUNCS`（9 個以上功能時會回 `INTERNAL`）。
10. **heap guard 跳過的畫面不發布（Task 1、4）**：`mxh_detect` 在記憶體不足（內部 < 32 KB 或 PSRAM 最大區塊 < 256 KB，同人臉；Task 1 依實測調整）或未初始化時回 `MXH_SKIPPED`（−1），處理流程把那張畫面當成「沒有新結果」：不快取、不推送、TFT 不畫框。理由：SPEC §10 已指出人臉把「跳過」當成「0 張臉」是錯的；新功能直接做對（人臉的修正留給 M4 項目，不在本計畫改）。
11. **TFT（Task 4）**：框 2 px；顏色：`id 1–9` 用 `k_id_colors[(id − 1) % 8]`（與 Studio `idColorVar` 相同，所以 9 倒讚和 1 同色）、`id 0` 用白色；標籤 `OK 92`／`HAND 81`（`mxh_label`，ASCII、照 ADR-0010 鏡像繪製，位置規則同現有 `draw_results`）；左上角功能名稱 `GESTURE`。
12. **Studio（Task 5、6）**：功能列新增「手勢辨識／Gesture」，lucide `Hand` 圖示，新分類色 `--cat-gesture: #29b6f6`（亮、暗兩組照 `--cat-face` 的寫法）；結果標籤：有名字用名字，否則用語系的手勢名稱，後面加信心度（`讚 92%`、`手 81%`）；結果分頁多一欄手勢；學習分頁「手勢辨識不需要學習（9 種固定手勢）」＋9 個手勢的取名表；參數分頁三個參數（範圍同設計決定 7，`max_hands` 是 1／2 二選一並提示「兩隻手較慢，約 3 fps」）；程式分頁 `MXCAM_ALGO_GESTURE`；展示模式：一隻卡通手每 1.5 秒換一個手勢（0–9 輪流），每 12 秒有一半時間出現第二隻手，辨識規則與韌體相同（門檻、排序、`max_hands`）；FakeFirmware 支援功能 8；設定檔（匯出／匯入）維持 `version: 1`，新增**可省略**的 `params.gesture` 與 `learned[8]`（名字，可以從檔案還原，和 AprilTag 一樣）。
13. **Arduino API（記錄給 M4，不在本計畫實作）**：`MXCAM_ALGO_GESTURE`（8）、`MXCAM_GESTURE_UNKNOWN`（0）、`MXCAM_GESTURE_ONE`…`MXCAM_GESTURE_DISLIKE`（1–9，值來自共用 C 的 `MXP_GESTURE_*`）。Studio 程式分頁的範例照這組名稱寫。

## 全域限制

- 協定只新增、不改既有欄位；新的測試資料只**加進** `docs/protocol-vectors.json`（不改既有項目），C 與 TS 都要通過；`encoded_hex` 的 CRC 用程式算（python 或 `encodeFrame`），不要手打
- `arduino-lib/src/protocol/` 維持純 C99（ADR-0006）；`MXP_RESULT_EXTRA_MAX` 維持 18；手勢紀錄 `extra_len` 0
- 座標一律 320×240 真實影像（ADR-0010）；辨識路徑上不做任何翻轉；TFT 文字只用 ASCII、鏡像繪製（`mxo_draw_text_mirrored`）
- `mxh_init` 只能在 `app_main` 建立 task 之前呼叫（ADR-0011、0019）；esp-dl 配置失敗會 abort，載入前與每張辨識前都要檢查記憶體
- 內部 RAM 最低剩餘 ≥ 60 KB；開機後 PSRAM 剩餘 ≥ 2 MiB；app 映像 ≤ 3,774,873 B；開機載入 ≤ 1 s（設計決定 2、3）
- 效能目標（SPEC §3，NN 功能）：一隻手 ≥ 3 fps（TFT，不串流與串流都要）；兩隻手不串流 ≥ 3 fps，串流時照實記錄
- 處理流程（core 1）不能因 USB 阻塞；推送走 `mxcam_link_push`；統計 log 每秒一行
- host test 的 CMake 參數照現有元件：`-std=c99 -Wall -Wextra -Werror`；新的 host test 加進 `.github/workflows/ci.yml` 的 host-tests job
- 本機驗證指令：

## 審查重點

1. **手在畫面邊緣、很小、或偵測框超出畫面**：裁切後的框不能是空的或太小，否則 esp-dl 的裁切／縮放可能 abort（整台重開機）。→ Task 1 `pick_hands_clip_and_min_size`；Task 7 把手移到畫面四個角落、拿遠到很小。
2. **兩隻以上的手**：只能分類前 `max_hands` 隻，處理時間不能隨手數增加；三隻手入鏡時不能變慢。→ Task 1 `pick_hands_threshold_sort`（3 個框、max 2 → 2 個）；Task 1 基準量兩隻手的時間。
3. **記憶體**：開機多載入兩個模型後，AprilTag／人臉仍要能跑；heap guard 跳過的畫面不能被發布成「0 隻手」；反覆切換功能不能漏記憶體。→ Task 4 冒煙測試（3↔8↔2 切換 30 次 heap 不降、各功能都有結果）；設計決定 10。
4. **舊的 NVS 資料（v1 blob）**：燒新韌體後顏色、名字、Config 必須還在，手勢參數用預設；之後的韌體寫的 v2（多了不認得的參數紀錄）也要讀得進來。→ Task 3 `deserialize_v1_fixture`、`v2_skips_unknown_record`。
5. **新舊版本混搭**：Studio 連舊韌體（沒有 8）時手勢選項停用、不送 `0x44`；韌體列出 8 但 `0x44` 回 `UNKNOWN_CMD` 時連線不能失敗；上游之後若多了新類別名稱，韌體要回 `id 0` 而不是亂對應。→ Task 5 `old firmware: no gesture func config request`、`func config unsupported drops gesture`；Task 1 `gesture_ids`（未知名稱 → 0）。
