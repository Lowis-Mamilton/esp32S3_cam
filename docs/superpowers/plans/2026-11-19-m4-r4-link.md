> 🧑‍🔧 步驟由主對話跟使用者一起做（需要實物：MATRIX Mini R4、BSS138 電位轉換模組、杜邦線、AprilTag／彩色物體）。直接在 `main` 上 commit；路徑 `C:\dev\esp32S3_cam`。
> 設計問題已由使用者授權「直接採用建議」；下方「設計決定」列出每個決定與理由，執行時依各 Task 的步驟寫進 SPEC／ADR／protocol.md。

**目標：** MATRIX Mini R4 透過 UART 或 I2C，用 Arduino 函式庫 `MXCam` 讀到顏色、AprilTag、人臉三種功能的結果，一次讀取延遲 ≤ 50 ms；R4 不接螢幕（或螢幕故障）時辨識照常運作。

**架構：** 先把 `mxcam_service` 改成與傳輸介面無關（`mxs_handle` 帶傳輸別、各傳輸自己的延後回應 outbox，以 seq 確認），state mutex 移到新的小元件 `mxcam_state`。新元件 `mxcam_r4link`：純 C、可主機測試的 `r4link_core`（解碼→`mxs_handle`→回應位元組佇列；I2C 讀取分段），加上碰硬體的 `r4_uart.c`（UART1，GPIO1/2）與 `r4_i2c.c`（I2C 從屬，v2 驅動，GPIO41/42）。Arduino 函式庫用共用的 C 協定碼（ADR-0006），UART 與 I2C 共用同一套 API。

**技術：** ESP-IDF v5.5.6（`driver/uart.h`、`driver/i2c_slave.h` v2：`CONFIG_I2C_ENABLE_SLAVE_DRIVER_VERSION_2=y`）；Arduino `arduino:renesas_uno` 1.6.0（UNO R4 WiFi／Minima，MATRIX Mini R4 用 R4 板型）；既有 React/TS。

**規格：** `docs/SPEC.md` §4（腳位）、§5、§6.1、§6.3、§8（M4 完成條件）、§10（M4 項目）；`docs/protocol.md` §3、§6、§7；ADR-0005、0006、0007、0011。

## 設計決定（執行時寫進 SPEC／ADR；理由附在後面）

1. **傳輸無關的 service（Task 1，ADR-0012）**：`typedef enum { MXS_TR_USB, MXS_TR_UART, MXS_TR_I2C, MXS_TR_COUNT } mxs_transport_t`；`mxs_handle(s, tr, req, now, out, cap)`。UART／I2C 上 STREAM_START／STOP 回 `NOT_SUPPORTED`（protocol.md §6 已規定）。只有 **USB** 的請求會更新 `last_request_ms`／`has_request`（串流逾時與 TFT 連線圖示），R4 輪詢不會讓串流維持、也不會點亮圖示；R4 另記 `r4_last_ms` 只給統計 log。延後回應的 outbox 改成每個傳輸一份（`outbox[MXS_TR_COUNT][MXS_DEFERRED_QUEUE]`），pending LEARN／SAVE 記住來源傳輸，回應送回同一個傳輸；`mxs_ack_deferred(s, tr, seq)` 以 seq 確認（M2 審查項目）。理由：R4 與 Studio 可能同時連著（Studio 用 USB 設定、R4 在跑），回應不能送錯孔；分開的 outbox 比在單一佇列加標記好測、好推理。
2. **state mutex 移到 `mxcam_state` 元件**：`mxcam_state_init/lock/unlock`，加上 `mxcam_state_register_kick(void (*)(void))`／`mxcam_state_kick_deferred()`，讓 pipeline／store worker 喚醒「所有」傳輸送延後回應。理由：UART／I2C 元件也要拿同一把鎖，元件不能依賴 `main`，也不該依賴 USB 元件。
3. **UART**：`UART_NUM_1`（UART0 是 console），TX=GPIO1、RX=GPIO2（照 SPEC §4「TX/RX=GPIO1/2」的順序；🧑‍🔧 實板核對，錯了只改兩個 define），8N1，鮑率取開機時的 `cfg.uart_baud`（115200／9600）。封包與 USB 完全相同；**一問一答、不主動推送**（R4 用 GET_RESULTS 輪詢；Arduino 端最簡單，且 SoftwareSerial／小緩衝不會被推送塞爆）。RX 緩衝 1 KB、TX 緩衝 2 KB（GET_LEARNED 最大約 1.75 KB），task 在 core 0、優先權 5。
4. **I2C 傳輸方式（Task 4，ADR-0013，protocol.md 新增 §8；SPEC §10「M4：I2C 傳輸方式定稿」）**：
   - 從屬位址取開機時的 `cfg.i2c_address`（預設 0x5A），SDA=42、SCL=41，`I2C_NUM_0`（鏡頭 SCCB 用新版驅動佔 port 1，見 sdkconfig `CONFIG_SCCB_HARDWARE_I2C_PORT1`），用 v2 從屬驅動（v1 將在 IDF v6 移除），開啟 `stretch_en`，內部上拉關閉（BSS138 模組上有上拉）。
   - **寫入**：R4 寫入的 bytes 就是 MX 請求封包的位元組流，可以分成多次寫入（每次 ≤ 32 bytes），MXCam 全部依序餵給同一個解碼器。收到新的完整請求時，丟掉這個傳輸上還沒被讀走的舊回應位元組（一問一答，舊答案只會造成混淆）。
   - **讀取**：R4 每次**固定讀 32 bytes**。第 0 個 byte 是 `N`（0–31），後面 `N` bytes 是回應位元組流的下一段，其餘填 0。`N = 0` 表示「還沒有資料」（回應還在算、延後回應、或根本沒問）。R4 把每段接起來餵給自己的解碼器，直到解出一個完整回應或逾時。
   - 理由：Wire 緩衝（R4 core 的確切大小開工時再查 `Wire.h`；AVR 是 32）、從屬端 TX FIFO 殘留（主機提早 NACK 會讓沒送出的 bytes 留到下次）兩個風險都靠「固定 32 bytes」避開；長度前綴讓 R4 不用先問長度再讀（少一次往返），也自然支援分段讀取大回應；不靠時脈延展等待計算完成（RA4M1 Wire 的延展逾時不保證），只在 `on_request` 補資料時短暫延展。
   - 時脈：R4 端預設 100 kHz（BSS138 模組在 400 kHz 邊緣），可用 `Wire.setClock(400000)` 自行加速。100 kHz 下每段 32 bytes 約 3 ms；4 筆顏色結果（63 bytes）3 段約 10 ms，4 個 tag（135 bytes）5 段約 15 ms，符合 ≤ 50 ms。
5. **無螢幕也能辨識（Task 3）**：`run_pipeline = camera_ok`；能力遮罩與 `mxf_init` 只看鏡頭（`mxf_init` 仍在建立任何 task 之前，ADR-0011）；`pipeline_start(state, boot_error, display_ok)`，顯示器不可用時跳過疊圖與 `mxcam_display_draw`（省時間，也不累加 `lcd_err`）。理由：R4 的教學情境可能不接 TFT；辨識不需要螢幕。
6. **Arduino 函式庫 API（Task 6）**：照 SPEC §6.3 與 Studio 程式分頁（`pc-app/src/ui/panel/codeSnippets.ts`）：`MXCAM_ALGO_NONE/COLOR/TAG/FACE`（0–3）、`begin(Stream&)`（使用者自己 `Serial1.begin(baud)`，和 Studio 範例一致）、`begin(TwoWire&, uint8_t addr = 0x5A)`（使用者自己 `Wire.begin()`）、`setAlgorithm`、`getAlgorithm`、`request()`、`available()`、`read()`、`count()`、`frameId()`、`forget(algo, id)`、`getLearned(...)`、`setTimeout(ms)`（預設 100 ms）、`lastError()`；`MXCamResult { id, x, y, width, height, confidence, angle }`（`angle` 只有 AprilTag 有意義，整數度；四角座標不在 v1）。`begin()` 送 GET_INFO，協定版本 1 才回 true。不做 LEARN／SET_NAME（學習在 Studio 做）。理由：與 HUSKYLENS 寫法接近、與 Studio 範例逐字相容；R4 端 RAM 小，解碼緩衝 512 bytes，GET_LEARNED 超過就回錯誤（文件註明）。
7. **函式庫發佈（Task 6，SPEC §10）**：M4 就做：`library.properties` 版本 0.1.0；新的 workflow `.github/workflows/arduino-lib-release.yml` 在 push tag `arduino-lib-v*` 時把 `arduino-lib/` 打包成 `MXCam-<版本>.zip`（`git archive --prefix=MXCam/`，排除 `extras/host-test`）上傳到 GitHub Release。Library Manager 登錄延後。CI 的 arduino-lib job 改成 matrix 編譯 `unor4wifi` 與 `minima`。
8. **M3 審查的順手項目**：
   - heap guard 跳過偵測：`mxf_detect` 回 `MXF_SKIPPED`（0xFF），pipeline 當成「沒有新結果」（不快取、不推送、不計入 face_ms，log 計數 `face_skip`）— 做（Task 3）
   - `FACE_EVERY` 路徑沒測試也不用：刪除，保留「不發佈」的分支給 skip 用 — 做（Task 3）
   - store `name_key_ok` 拒絕人臉 key（SET_NAME 本來就擋，所以 NVS 裡不會有人臉名字）— 做（Task 3）
   - Studio 灰色訊息：韌體版本改成 0.4.0（M4）；Studio 在韌體 ≥ 0.4.0 卻沒有功能 3 時顯示「人臉初始化失敗」，否則「需要更新韌體」— 做（Task 7）
   - outbox 以 seq 確認 — 做（Task 1）
   - C 端 FORGET 打包、GET_LEARNED 解析給 Arduino 用 — 做（Task 6）
   - AprilTag 信心度縮放：維持 `clamp(decision_margin, 0, 100)`，把滿分值抽成 `MXT_MARGIN_FULL`（100，行為不變）；🧑‍🔧 實測時記錄實際 margin 分佈，有資料再調 — 只抽常數（Task 3）
9. **實機接線（Task 8，⚠️ 要使用者確認）**：ESP32-S3 的 GPIO **不耐 5 V**；R4（RA4M1）以 5 V 邏輯運作，UART 與 I2C 一律經 BSS138 模組（LV＝ESP32 板 3.3 V、HV＝R4 5 V、**兩邊 GND 共地**）。兩塊板子各自供電（ESP32 用 USB、R4 用自己的電源），不要把 R4 的 5 V 接到 ESP32 板的 3.3 V 腳。

## 全域限制

- 協定封包、指令、錯誤碼以 `docs/protocol.md` 為準；I2C 傳輸只新增 §8，不改既有欄位；新增測試資料只能加進 `docs/protocol-vectors.json`，C 和 TS 都要通過
- 畫面處理流程（core 1）永遠不能因任何傳輸阻塞；UART／I2C task 在 core 0
- 除錯 log 只走 UART0（TTL 埠）；`mxcam_r4link` 不可以 log 到 UART1
- R4 的請求不影響串流逾時、TFT 連線圖示（只有 USB 算）
- 內部 RAM：最低剩餘仍需 ≥ 60 KB（M3 量到約 105 KB，留給 UART／I2C 的餘裕約 45 KB）；大緩衝放 PSRAM
- UART 鮑率、I2C 位址只在開機時讀 config（存檔並重開機才生效，protocol.md §7）
- `arduino-lib/src/protocol/` 維持純 C99（ADR-0006），不可引用 Arduino 或 ESP-IDF 標頭
- 既有主機測試全部維持綠燈；指令見 CLAUDE.md「電腦上的 C 測試」
- 本機沒裝好 ESP-IDF 時不要宣稱「已建置成功」；`idf.py build` 用 PowerShell 啟用 `C:\Espressif` 的環境
- commit 訊息結尾加 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`

## 審查重點

1. **回應送錯孔**：Studio（USB）與 R4（UART／I2C）同時發請求、同時有延後回應（SAVE、LEARN）時，回應必須回到發問的傳輸、seq 正確；一個傳輸沒人讀時不能卡住另一個。→ Task 1 測試 `deferred_goes_back_to_its_transport`、`ack_by_seq_keeps_other_entries`
2. **R4 輪詢偷偷維持串流**：Studio 關掉後只剩 R4 每 50 ms 輪詢，3 秒後串流必須停、TFT 圖示變空心。→ Task 1 測試 `r4_requests_do_not_keep_stream_alive`
3. **I2C 讀到舊資料或殘段**：R4 重開機、讀到一半放棄、或兩次請求間沒讀完，下一個回應不能夾著舊 bytes。→ Task 4 測試 `new_request_drops_unread_response`、`chunk_never_exceeds_31_bytes`、`garbage_then_valid_request`
4. **鮑率／位址設定錯誤**：NVS 裡的鮑率不是 115200／9600、位址不在 0x08–0x77 時要用預設值（codec 已夾限，r4link 仍以 `mxp_config_t` 為準不再自己解析）；開機 log 印出實際使用的值。→ Task 5 開機 log 步驟
5. **無螢幕開機**：拔掉 TFT 排線開機，R4 仍能切功能、讀到結果，log 沒有 `lcd_err` 狂增。→ Task 3、Task 8 實機步驟
